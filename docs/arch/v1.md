## 1. 先建立 MVP，再進行研究

先完成「提交需求 → 排隊 → 分配 → 實際執行 → 釋放資源 → 保留紀錄」的驗證鏈，
再固定其他條件，逐項比較 baseline 與研究方法。AI 協助實作與蒐證，不代替研究假設及驗收判斷。

| 階段 | 我們要得到什麼 | AI 可以協助的工作 |
| --- | --- | --- |
| 建立 MVP | 工作可以從提交一路到釋放資源，每個步驟都有紀錄 | 實作 module、adapter、測試與執行腳本 |
| 驗證機制 | 給定一個情境，事先寫出預期，再核對實際結果 | 產生固定情境、收集紀錄、找出差異 |
| 研究方法 | 固定其他條件，比較 baseline 與一項研究改動 | 實作已確認方法、重跑實驗、整理結果 |

研究方向仍有三層，但第一版 Rust 實作上兩層；Pod 層使用既有 HAMi 能力，
除非後續研究確實需要，否則不開發或修改 HAMi-Core。

| 研究層 | 第一版 baseline | 後續方向 |
| --- | --- | --- |
| Cluster | 固定租戶額度、租戶間加權輪詢 | DQA；歷史行為影響治理決策 |
| Job | 租戶內 FIFO、可行性檢查與 GPU 放置 | FWA／GFS／topology-aware placement |
| Pod | HAMi 實際排程、配置與既有隔離能力 | 必要時驗證並整合 HAMi-Core 執行期保護 |

Prometheus 與執行紀錄是跨層觀測，不是第四個研究層，也不擁有排程 policy。
第一版只記錄歷史，不自行發明歷史評分、預測公式或動態調整門檻。

## 2. 實驗平台與記憶體語意

- 實機基準是單張 GB10 與 k3s cluster；多個虛擬 node 不代表多張實體 GPU。
- 預設 96 GB 是可設定的 GPU 邏輯實驗預算，不是統一記憶體的物理切割或硬隔離保證。
- UI 分別顯示系統 RAM 總量、可用量、採樣時間及實驗預算；未取得資料時顯示未知。
- GB／GiB 與後端儲存單位須在實作契約中明訂，不能默默把 96 GB 換成 96 GiB。
- 需求量、預留量與實際配置結果分開記錄；尚在配置中的預留也必須計入預算。
- 不使用 vLLM。工作配置固定大小的 GPU 記憶體、寫入並同步，佔用指定時間後釋放。
- 真實配置成功須有 workload 回報與執行證據，不能只用 Pod `Running` 當作證明。

HAMi 註冊容量、邏輯預算與系統可用記憶體不是同一個值；共享名額不能乘成實體容量。
邏輯預算檢查也不能代替實機容量及 HAMi 可行性檢查。
單卡實驗驗證真實執行鏈；多 GPU placement 先使用固定合成快照測試相同 Job module，
合成結果不冒充真實多卡或 topology 效益。

## 3. 最小需求單位：DesiredGpuPod

以 CRD 定義 `DesiredGpuPod`，每個 CR 代表一次 GPU 工作需求，不是維持副本數的 RC。
合法需求正式提交後先存在 Kubernetes；Rust 安排執行時才建立實際 Pod，不以移除 gate 為主流程。

| 部分 | 第一版需要表達的內容 |
| --- | --- |
| `spec` | 所屬租戶 Queue、GPU 記憶體需求、固定佔用時間、等待模式與選填期限 |
| `status` | 執行狀態、等待／失敗原因、預留與配置資訊、對應 Pod、時間紀錄 |

這是語意契約，不是已定稿的 CRD 欄位 schema。
需求與執行狀態由 Kubernetes 保存，不另建一份 runtime database。
UI 與研究候選以 `DesiredGpuPod` 為主；後端仍觀察 Queue、GPU inventory 與實際 Pod，
才能知道配置結果、外部占用與何時可釋放資源。

提交與重跑的規則：

- 單筆需求超過允許的總預算，直接拒絕，不進入 `Waiting`，不建立執行 Pod。
- 需求合理但當下放不下，正式接受後進入 `Waiting`，交由 Rust 調度。
- 一份需求只執行一次；重複 reconcile 不代表建立新 Pod 或重新執行。
- 完成、失敗或逾時後保留 CR 與結果，不自動補建或重跑。
- 管理者拖動重跑時沿用設定建立新需求，舊紀錄不覆寫。

## 4. 兩層 Queue 與調度 baseline

### 4.1 Cluster 治理 queue

Cluster 治理 queue 管理租戶之間的資源競爭與調度機會；它不是第二份 Pod 需求清單，
也不代表第一版必須再建立一種父 queue CRD。

- 額度：租戶可使用的上限。第一版使用可修改的固定設定，不自動借用其他租戶的閒置額度。
- 權重：租戶取得調度機會的比例。第一版預設 `1`，可設定為不同值。
- 第一版採加權輪詢；雙方皆可執行時，權重 `2:1` 表示調度機會按此比例分配。
- 權重不保證記憶體用量或 GPU 執行時間同樣是 `2:1`，也不會提高租戶額度。
- 無候選、額度不足或隊首無法放置時，跳過該租戶，繼續檢查其他租戶。

雙租戶各 48 GB 是總預算 96 GB 下的預設實驗範例，不是寫死的租戶數或研究公式。
固定額度與後續 DQA 都由 Cluster module 產生治理結果；UI 與 controller 不各算一份。
加權輪詢的進度不能在每次 reconcile 都重設；重啟後的恢復行為須有可重現測試。

### 4.2 租戶 queue

每個 `DesiredGpuPod` 屬於一個租戶 Queue，租戶內採嚴格 FIFO。
同租戶隊首暫時放不下，後面的需求不能超車；這不要求其他租戶也一起等待。

Job module 在 Cluster 給定的額度與租戶次序下，檢查隊首可行性並產生 GPU 放置決策。
HAMi 負責實際排程與配置，但不能靜默改到 Rust 允許範圍以外的 GPU。
傳遞放置限制的 HAMi adapter 必須有實機整合證據，不能只證明 Rust 算出了結果。

## 5. Waiting、執行與終止

`Waiting` 從正式接受合法需求起，到實際配置成功前為止。
對外不另立 `Starting` 主狀態，但內部仍區分排隊中與分配中。

| 狀態／內部分類 | 意義 | Rust 的責任 |
| --- | --- | --- |
| `Waiting`：排隊中 | 未輪到、額度或 GPU 空間不足 | 隨觀測與調度事件重新評估，不能重複建立 Pod |
| `Waiting`：分配中 | 已預留額度，正在建立或等待既有 Pod 配置 | 追蹤同一次嘗試，預留額度不能再次分配 |
| `Running` | 固定 GPU 記憶體已配置成功，正在佔用 | 觀察工作結果；等待期限不再充當執行期限 |
| `Succeeded` | 工作正常完成 | 確認資源已釋放，保留紀錄 |
| `Failed` | 本次配置或執行明確失敗 | 確認收尾，保留原因，不自動重跑 |
| `TimedOut` | 限時等待到期，尚未完成配置 | 停止該次待執行嘗試並收尾，保留紀錄，不自動重跑 |

### 5.1 兩種等待模式

| 模式 | 行為 |
| --- | --- |
| 永久等待（預設） | 沒有等待期限；Rust 持續安排，直到配置成功或本次嘗試明確失敗 |
| 限時等待 | 明確設定期限；正式接受起算，期限內未完成配置就以逾時結束 |

同一需求從排隊轉入分配中、重新評估或 controller 重啟，都不重設等待起點。
永久等待不是忙迴圈，也不是明確失敗後無限重跑。
暫時無法取得觀測、寫入結果不明或單次評估放不下，不能直接冒充工作失敗。

### 5.2 收尾與資源帳務

預留、實際占用與終止結果須分開處理；不能因為 UI 顯示失敗或逾時，就立即把額度放回去。
已有實際 Pod 時，收尾必須確認它不再占用、也不再可能取得該份資源，才能釋放預留。
逾時與配置成功同時發生時須重新核對實際結果，避免重複分配或讓終止需求繼續執行。
完成與失敗紀錄不回到 `Waiting`；手動重跑產生新的需求 identity。

## 6. 單一 Rust 後端與 Module Interface

第一版用單一 Rust 後端程序／部署單位，內部按責任組織 module，不先拆成多服務或多 crate。

| Module／adapter | 擁有的責任 | Interface 的主要輸入與輸出 |
| --- | --- | --- |
| `cluster` | 租戶額度與加權輪詢；後續接入歷史治理 | 設定、租戶快照與輪詢進度 → 額度、租戶次序與下一進度 |
| `job` | 租戶內 FIFO、需求可行性與 GPU 放置 | 治理結果、需求與 GPU 快照 → 放置決策或等待原因 |
| `workload` | 需求生命週期、等待期限與預留／釋放規則 | 當前狀態、時間、決策與觀測 → 下一狀態及待執行動作 |
| `application` | 串接觀測、決策與動作；UI 預覽、提交與查詢 | 使用者操作或 reconcile 事件 → 執行 domain 決策並回傳結果 |
| Kubernetes／HAMi adapter | 外部物件轉換、資源讀寫與執行結果觀測 | 外部資料 ↔ domain 需要的最小 representation |

Domain 使用 pure function 或 small struct，回傳決策而非直接做 I/O。
Controller／application 不擁有研究 scoring，adapter 不自行決定 quota 或 placement。
UI、實驗腳本與測試使用相同 interface；預覽只評估，正式執行才提交動作。
時間、排序、輪詢進度、錯誤模式與資源 invariant 都屬於 interface，不只是一組函式參數。
不預建未使用的 plugin framework 或 generic trait；遵守 [Deep Module Design](../dev/deep-module-design.md)。

## 7. UI 操作語意

- 顯示 RAM 狀態、實驗預算、租戶 Queue 與需求卡片；雙擊查看設定、狀態和原因。
- 前端送出需求給 Rust 預覽；可行卡片高亮。預覽唯讀，不建立 CR、Pod 或資源預留。
- 正式拖入執行區才提交；後端以最新狀態重新驗證，合法需求進入 `Waiting`。
- 提交不是直接取得資源；仍須遵守加權輪詢、FIFO 與額度，在實際安排時預留資源。
- 高亮只表示快照下可行，不保證立即執行，也不能繞過 queue。
- 需求合理但目前不足時，卡片可回彈並顯示等待原因；已接受的需求仍由 Rust 排隊處理。
- 普通拖移只改 UI；回彈不是刪除或驅逐 Pod。只有明確的提交／重跑操作才改變需求。
- 終止卡片保留，管理者拖動重跑建立新需求，不清掉舊結果。

## 8. 重構順序與 MVP 驗收

| 階段 | 交付內容 | 必要驗證 |
| --- | --- | --- |
| 1. 開發入口 | 固定工具版本、統一驗證方式、無 cluster 的 domain 開發路徑 | 乾淨環境能重現編譯與測試 |
| 2. Domain 與責任拆分 | 先拆 oversized controller，再建立治理、放置與生命週期 interface | 固定快照驗證額度、加權輪詢、FIFO、兩種等待與失敗處理 |
| 3. CR 與實際執行鏈 | `DesiredGpuPod`、預留、Pod、HAMi adapter 與固定記憶體 workload | 真實配置／釋放、重啟恢復、不重複建立與逾時收尾 |
| 4. 簡單 UI | 預覽、提交、狀態、雙擊設定與手動重跑 | 預覽不寫入；資源變動後提交仍安全；重跑不覆寫紀錄 |
| 5. 實驗驗證鏈 | 固定情境、預期結果與 run artifacts | 拒絕、等待、成功、失敗、逾時與完整資源釋放都有證據 |

每次實驗保留需求、有效配置、額度／權重、等待模式、時間點、原因、Pod identity、
workload 結果及部署版本；預留量不冒充實際使用量，缺失觀測不冒充零值。
等待從需求正式接受起算，分開記錄排隊與分配耗時；不能直接等同實際 Pod Pending 指標。

Rust 變更依 [AGENTS.md](../../AGENTS.md) 依序執行 fmt、check、clippy、test。
只有 deployment／Kubernetes behavior 改變時追加 smoke 或 experiment；本次文件整理不操作 cluster。
